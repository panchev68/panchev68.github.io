IAR EWARM Library

Header-only C++20 embedded systems library for IAR Embedded Workbench with STM32F4xx MCUs, providing hardware abstraction, RTOS integration, and communication protocols.

📖 Overview

The IAR EWARM Library is a header-only C++20 library for embedded systems development on STM32F4xx microcontrollers using IAR Embedded Workbench 10.10.2. It provides a type-safe interface to hardware peripherals, FreeRTOS abstractions, communication protocols, and board-support drivers. The library abstracts low-level HAL details while maintaining direct access to hardware capabilities through multiple transfer modes (blocking, interrupt-driven, DMA) and supports CAN bus communication, EtherCAT slave operation, Modbus, and the Digi/XBEE and XCOM protocol stacks.

It is almost entirely header-only (inc/Lib/**/*.hpp) and is not built or tested standalone — it's consumed by an IAR project such as the sample one under EWARM/.

🚀 Features

  • Hardware Abstraction Layer (HAL): Type-safe wrappers for STM32 peripherals (SPI, UART, I2C, CAN, ADC, DAC, timers, GPIO, RTC, watchdogs, USB, OSPI/Quad-SPI)
  • FreeRTOS C++ Wrappers: Tasks, queues (incl. queue sets), semaphores, mutexes, event groups, software timers, message/stream buffers, tickless low-power support
  • Communication Protocols: CAN bus client/server, EtherCAT slave (direct ESC-register implementation), Modbus master/slave (incomplete), Digi XBEE API, XCOM data protocol
  • Multiple Transfer Modes: Blocking, interrupt-driven, and DMA I/O for SPI, UART, I2C, and ADC
  • Board Support Package (BSP): Ready-to-use drivers for displays (ILI9341, ST7789), touchscreens, EEPROMs, flash memory, RFID (MFRC522, ST25R100, NTAG21x), thermometers, voltmeters, RGBW LEDs, encoders, and more
  • Error Handling: Centralized error state machine with dispatcher/observer pattern
  • USB Support: Host/device port wrappers over the STM32 USB OTG HAL
  • Doxygen Documentation: API documentation generated from inline comments

🏗️ Architecture

The library is organized in a modular, layered architecture:

┌─────────────────────────────────────────────────────┐
│ Application Layer (User Code) │
├─────────────────────────┬───────────────────────────┤
│ BSP Device Drivers │ Communication Protocols │
│ (Display, RFID, ...) │ (CAN, EtherCAT, Modbus, │
│ │ Digi/XCOM) │
├─────────────────────────┴───────────────────────────┤
│ C++ RTOS Wrapper Layer (FreeRTOS) │
│ Tasks, Queues, Semaphores, Timers, Events │
├─────────────────────────────────────────────────────┤
│ Hardware Abstraction Layer (HAL) │
│ SPI, UART, I2C, CAN, ADC, DAC, TIM, GPIO, USB │
├─────────────────────────────────────────────────────┤
│ STM32F4xx HAL (C) & Hardware Registers │
└─────────────────────────────────────────────────────┘

Core Components:

  • HAL (Lib::HAL): Peripheral drivers templated on transfer mode (DriverMode::BLOCKING/IT/DMA), CRTP over a shared *PortBase/*PortAsync policy class per peripheral
  • RTOS (RTOS::, top-level namespace, not Lib::RTOS): FreeRTOS C++ wrappers for real-time task management
  • Communication: Lib::Canbus (client/server), Lib::Ethercat (SOES slave stack), Lib::Communication::Modbus, Lib::Digi, Lib::XCOM
  • BSP (Lib::BSP): Board-specific device drivers, each taking its transport as an injected Lib::HAL::*Port reference
  • Errors (Lib::Errors): Centralized error handling and diagnostics
  • System (Lib::System): Platform initialization, versioning, and configuration utilities

📋 Requirements

  • Compiler: IAR Embedded Workbench 10.10.2 (iccarm.exe), Libc++20
  • Platform: STM32F4xx microcontroller series (developed against STM32F407xx)
  • RTOS: FreeRTOS (via STM32Cube middleware)
  • Optional: TouchGFX (for UI/graphics support, via the TouchGFX project connector)
  • Build System: IAR Embedded Workbench project files (.ewp/.eww)
  • C++ Standard: C++20 with Libc++, no exceptions, no RTTI

🔧 Installation

Integration with IAR Embedded Workbench

The library integrates into a new, separate IAR project via IAR Project Connectors (.ipcf files) under ProjectConnectors/ (right-click the project → "Add Project Connection..."). Apply in numbered order:

  1. 1.Project-startup.ipcf — wires up include paths and a starter Project/Startup.cpp entry point
  2. 2.FreeRTOS_Support C++.ipcf — adds the FreeRTOS kernel and RTOS C++ wrapper support
  3. 3.Doxygen.ipcf — integrates Doxygen documentation generation
  4. 4.TouchGFX Support.ipcf (optional) — adds TouchGFX UI framework support, including display drivers (ILI9341, XPT2046)

See ProjectConnectors/CLAUDE.md for details on what each connector copies and known stale references to watch for.

▶️ Usage / Quick Start

Basic Peripheral Access (SPI Example)

#include <Lib/HAL/SPI.hpp>
#include <array>
#include <chrono>
// Create a blocking-mode SPI port bound to a CubeMX-generated handle
Lib::HAL::SPIPort<Lib::HAL::DriverMode::BLOCKING> spiPort(&hspi1);
if (!spiPort.open()) {
// Handle initialization error
}
std::array<uint8_t, 2> txBuffer{0xAA, 0xBB};
std::array<uint8_t, 2> rxBuffer{};
if (spiPort.sendReceive(txBuffer, rxBuffer, std::chrono::milliseconds(1000))) {
// Transfer successful
}
spiPort.close();

FreeRTOS Task Creation

#include <RTOS.hpp>
RTOS::Task myTask;
const RTOS::Task::Config config{"MyTask", 256 /* stack words */, RTOS::Task::Priority::NORMAL};
if (myTask.start(config, [] {
while (true) {
// Task logic
RTOS::delay(std::chrono::seconds(1));
}
}) != nullptr) {
// Task started successfully
}

CAN Bus Communication

`Lib::Canbus::Service<Mode::SERVER>`/`Service<Mode::CLIENT>` have protected constructors — derive your own class:

#include <Lib/Canbus/Template.hpp>
class MyCanServer final : public Lib::Canbus::Service<Lib::Canbus::Mode::SERVER> {
public:
explicit MyCanServer(CAN_HandleTypeDef * handle) :
Service(handle) {
}
};
MyCanServer canServer(&hcan1);
if (!canServer.start()) {
// Handle error
}
if (!canServer.send(/* nodeId */ 1)) {
// Handle transmission error
}

⚙️ Configuration

Key Configuration Files

  • inc/Lib/HAL/core/DriverMode.hpp: Defines the transfer-mode enum (BLOCKING, IT, DMA)
  • EWARM/Core/Inc/FreeRTOSConfig.h: FreeRTOS configuration parameters
  • EWARM/Core/Inc/stm32f4xx_hal_conf.h: STM32 HAL module enablement (e.g. HAL_SPI_MODULE_ENABLED) — a peripheral driver guarded by a macro not defined here compiles to nothing
  • inc/Lib/System/: Platform-specific initialization, versioning, and configuration storage

Common Configuration Options

  1. Transfer Modes: Select blocking, interrupt-driven, or DMA I/O per peripheral instantiation
  2. Task Priorities: Configure FreeRTOS task scheduling via RTOS::Task::Config
  3. Queue Sizes: Adjust RTOS::Queue<T, N> capacities
  4. Peripheral Clocking: HAL clock configuration (via STM32CubeMX, EWARM/Core/)
  5. Memory Layout: Stack/heap allocation in the linker script (EWARM/EWARM/stm32f407xx_flash.icf)

🎯 Architecture Components

Hardware Abstraction Layer (Lib::HAL)

  • SPI / UART / I2C: Blocking, interrupt-driven, and DMA modes
  • CAN: CAN controller integration (`CANPort`)
  • ADC / DAC: Analog I/O, with blocking/IT/DMA ADC modes
  • GPIO: Digital I/O, input/output handles, external interrupts
  • TIM: Timebase, PWM output, input capture, encoder, one-pulse, low-power timer
  • RTC / IWDG / WWDG: Real-time clock and independent/window watchdogs
  • USB: Host and device OTG port wrappers
  • OSPI: Quad-SPI/OCTOSPI (not available on STM32F407 — F7/H7/L4+ only)

RTOS Abstractions (RTOS::)

See the FreeRTOS wrapper index in CLAUDE.md for the full list — `Task`, `Queue`, `QueueSet`, `Semaphore`/`SemaphoreCounting`, `Mutex`, `EventGroup`, `Timer`, `MessageBuffer`, `StreamBuffer`, `TickClient`, `PowerManager`, and more.

Communication Protocols

  • CAN Bus (Lib::Canbus): Client/server service pattern over `Lib::HAL::CANPort<DriverMode::IT>`
  • EtherCAT (Lib::Ethercat): Slave implementation written directly against ESC registers; the vendored SOES C stack under native/ sits unused
  • Modbus (Lib::Communication::Modbus): Master/slave over a serial transport — ⚠️ incomplete
  • Digi/XBEE (Lib::Digi): XBEE API-mode frame protocol
  • XCOM (Lib::XCOM): Custom data transfer protocol
  • HTTP (Lib::HTTP): Transport-agnostic HTTP/1.1 client, with a wolfSSL-backed TLS wrapper for HTTPS, over any raw byte-stream link (Ethernet socket, GSM module, ...)
