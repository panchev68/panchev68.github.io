IAR EWARM Library

Header-only C++20 library for STM32F4xx microcontrollers: a hardware abstraction layer, C++ wrappers over FreeRTOS, board support drivers and several communication-protocol stacks, built with IAR Embedded Workbench for ARM.

What the project is

The library is consumed as source: every module lives in a header under 'inc/Lib' and nothing is compiled on its own, so a firmware project only adds 'X:/Lib/IAR/inc' to its include path. The current version is '3.08.0', kept on the GitHub branch '3.08' of 'panchev68-Library/IAR'. The IAR project in 'EWARM' is generated by STM32CubeMX and holds only test code that exercises the library on one board.

That test board carries an STM32F407VETx in an LQFP100 package, clocked from a 25 MHz external crystal to a 120 MHz core clock. The test firmware runs FreeRTOS through the CMSIS-RTOS V2 wrapper with a single default task, and links wolfSSL 5.9.2 as a CubeMX third-party package for the TLS and SSH helpers of Lib::Crypto. The scheduler is preemptive, and the tickless-idle low-power support is enabled through the 'FREERTOS_LOW_POWER_SUPPORT' define, which RTOS::PowerManager builds on.

The code is written for a freestanding target: exceptions and RTTI are off, virtual dispatch is replaced by CRTP and tagged enumerations, and heap allocation is limited to the FreeRTOS heap, to which 'malloc', 'free', 'operator new' and 'operator delete' are routed. Peripheral drivers are templated on the transfer mode (blocking, interrupt or DMA) and share their lifecycle and synchronization policy in a common base class.

Several parts are still missing or limited. There are no automated tests: verification is manual, on the target, through the IAR debugger. The F407 has no OCTOSPI and no HASH peripheral, so 'Lib::HAL::OSPIPort', the OSPI flash driver and the hardware engine of Lib::Crypto::SHA256 compile to nothing on this chip and are checked only against an STM32F417 definition. The TouchGFX layer is reserved in the project structure, but the test project has no display and does not use it. The ThreadX-based replacements for 'std::thread' and related types were removed and archived, so no standard threading facility is available.

Layers

Lib::HAL is the lowest layer: drivers for ADC, CAN, DAC, flash, GPIO, I2C, SPI, UART, USB, timers and the watchdogs, built on the ST HAL and shared through the mode templates and a handle-to-instance lookup for interrupt callbacks. Lib::BSP sits on top of it with drivers for the external components on the board: displays, EEPROM, flash and RAM chips, RFID readers, thermometers, current monitors, LED strips and a GSM modem, each taking its transport as an injected HAL port.

RTOS is the one top-level namespace outside 'Lib': RAII wrappers over the FreeRTOS tasks, queues, semaphores, mutexes, timers, event groups and stream buffers. The protocol stacks, Lib::Canbus, Lib::Communication, Lib::Digi, Lib::Ethercat, Lib::Ethernet, Lib::HTTP and Lib::XCOM, are built on the layers below. Supporting code is split into Lib::Helper for conversions and containers, Lib::Math for filters, interpolation and error-correcting codes, Lib::Crypto for hashing and TLS, Lib::Errors for the error dispatcher and Lib::System for firmware information, reset state and the freestanding exception type. Application-level modules such as Lib::Pneumatics and Lib::SolarControl use all of them.

Build requirements

The compiler is IAR Embedded Workbench for ARM '10.10.2', installed at 'C:/iar/ewarm-10.10.2', using the C++20 library selected by '–c++ –libc++', with '–no_exceptions –no_rtti' and the Cortex-M4 target with the single-precision FPU ('–cpu=Cortex-M4 –fpu=VFPv4_sp'). The project defines 'USE_HAL_DRIVER', 'STM32F407xx', 'STM32_THREAD_SAFE_STRATEGY=4', 'FREERTOS_LOW_POWER_SUPPORT' and 'configUSE_QUEUE_SETS=1'; the exact include paths are in 'EWARM/EWARM/Lib.ewp'.

The HAL and the kernel come from the STM32CubeF4 firmware package 'STM32Cube FW_F4 V1.28.3' in the user's 'STM32Cube/Repository' folder. It carries FreeRTOS kernel 'V10.3.1' with the CMSIS-RTOS V2 wrapper, API version '2.1'. The project is generated with STM32CubeMX '6.18.1' from 'EWARM/Lib.ioc'. wolfSSL '5.9.2' is added as a CubeMX third-party package.

To build, open 'EWARM/EWARM/Lib.eww' in the IDE and build the 'Lib' configuration, or build 'EWARM/EWARM/Lib.ewp' with the IAR VS Code extension or 'iarbuild'. CubeMX offers 'EWARM V8.50' as its newest toolchain, so it cannot target the 10.10 workbench and the project file is maintained by hand; regenerating the code rewrites 'EWARM/Core', so code outside the 'USER CODE' sections is lost, and 'FreeRTOSConfig.h' and 'stm32f4xx_hal_conf.h' must be checked afterwards. Copying the wolfSSL package into the project folder makes the generation very slow.

The documentation is generated with Doxygen '1.18.0' from '.doxygen/Lib.doxyfile'. It links to two tag files in the same folder: 'libstdc++.tag' for the standard library and 'HAL_F4.tag' for the ST HAL. Graphviz is not used.

Where to start

Begin with Lib::HAL for the peripherals and RTOS for the operating-system layer, then follow one driver in Lib::BSP from its configuration structure to the injected port. Each module has a 'Readme.md' next to its headers in 'inc/Lib', and several have a 'doc' folder with detailed notes. Usage examples are listed in the Examples tab, one per class, and every example is compiled against the current headers before it is published.

Some conventions are easy to miss. Peripheral ports are specialized per transfer mode and never use virtual inheritance. A BSP driver receives its transport as a reference to a HAL port, so the task that owns the bus owns the port. 'Lib::HAL::core::DeviceManager' maps a raw HAL handle back to its C++ instance inside a callback, and 'Lib::BSP::DeviceManager' is an unrelated class that runs periodic device updates on one timer. Methods that may be called from an interrupt end in 'FromISR'. Every library header carries the same '
