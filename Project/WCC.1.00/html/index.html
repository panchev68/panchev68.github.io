WCC Firmware

Firmware of a solar-powered waste-container controller: it admits users with an RFID card, opens a 5 l or 20 l client door, supervises the door, reports every event to an ESP32 communication module and keeps its own accumulator charged from a solar panel.

Hardware

The controller is built around an STM32U575VGT6 (Cortex-M33) running FreeRTOS. A 12 V solar panel charges a gel accumulator through an LMR14030 buck regulator whose output is set by a DAC; two INA219 monitors (panel 0x40, accumulator 0x41) and a TMP102 (0x48) on I2C1 feed the MPPT algorithm. Cards (NTAG21x) are read by an ST25R100 on SPI3. The fill level is measured by a PGA460 ultrasonic sensor on USART1 (115200 baud, 8N2), the outside temperature by a DS18B20 on a 1-Wire line. A W25Q128 flash (16 MiB) on OCTOSPI1 keeps the card blocklist, the service-card list and the disposal records that could not be sent. The ESP32 module on USART3 owns the connection to the central system. OUT1..OUT4 are BTS724G 12 V switches (OUT1/OUT2 the 5/20 l client locks, OUT3 the main door lock opened by a service card), supplied from an MT3608 12 V booster that is switched on only when a lock pulse or a distance measurement needs it. Two buttons with LEDs, two door sensors and a buzzer form the front panel.

How the firmware works

Every module in Application Layer is a singleton that owns its task, brings up its own hardware with retry inside that task and publishes its results through atomic getters. An accepted card (verified by APP::RFID: NXP originality signature and ECDSA P-256 record, then the blocklist) starts APP::UserInterface, which waits for the 5 l or 20 l button, pulses the lock, supervises the door and queues one disposal record. The ESP32 is the master of the link described in APP::Commands: it asks for the status, the records and the measurements, and the controller only answers; APP::ComModule powers the ESP32 on demand and wakes it when something is pending. The whole system is built for low power: FreeRTOS tickless idle drops into STOP1 through APP::LowPower, the 12 V rail and the INA219 monitors are switched off whenever possible, and the solar charger, the RFID wake-up and the distance measurement scale back at night or when the panel gives no usable power.

Still pending: the final release switches of APP::Application (the self-tests in Application Tests are removed before release), the end-to-end test with the ESP32 and the central system, and the field tuning of the ST25R100 wake-up range.

Layers

Hardware Abstraction Layer holds the concrete peripheral port instances, one singleton per CubeMX handle. Board Support Package holds the board I/O singletons and the thin board-wiring facades over the shared library chip drivers. Application Layer holds the functional modules, APP::Diagnostics and APP::Application, which starts everything. APP::Commands lists the ESP32 frame types. The on-target self-tests are the group Application Tests.

Build requirements

Compiler: IAR EWARM 10.10.2 ('C:/iar/ewarm-10.10.2'), C++20 with libc++ ('–libc++', never together with '–dlib_config'), no exceptions and no RTTI. Project: 'EWARM/STM32U575VGT6.ewp', configuration 'STM32U575VGT6'; the full build is 'C:/iar/ewarm-10.10.2/common/bin/IarBuild.exe EWARM/STM32U575VGT6.ewp -build STM32U575VGT6'. Generated code: STM32CubeMX 6.18.1 with the firmware package 'STM32Cube FW_U5 V1.9.0'. Kernel: FreeRTOS 11.2.0 with the CMSIS-RTOS2 wrapper shipped in 'Middlewares/' (the 'ARM_CM33_NTZ' IAR port). Shared library: header-only company library in 'X:/Lib/IAR/inc', branch '3.08', read-only from this project. ECDSA verification: micro-ecc in 'ThirdParty/micro-ecc'. Documentation: Doxygen 1.18.0 with the tag file of the shared library ('X:/Lib/IAR/.doxygen/Library.tag'), configured by 'WCC_Firmware.1.00.doxyfile'. CubeMX regeneration overwrites everything outside the 'USER CODE' blocks and resets the settings the firmware depends on: the LPTIM1 interrupt must stay disabled in CubeMX (the low-power code in 'APP/PowerSupply/LowPower.cpp' owns it) and the HASH data type must stay 'HASH_DATATYPE_8B'.

Where to start

Read 'RTOS/FreeRTOS_Support.cpp', which calls 'startup()' in 'Project/startup.cpp', then APP::Application, which starts every module according to its 'ENABLE_*' switch. Peripherals are reached through the singletons of Hardware Abstraction Layer, for example 'HAL::Usart1Port::instance()', and each bus has one owner task: USART1 the distance meter, SPI3 the RFID, I2C1 the power supply, OCTOSPI1 the storage manager, USART3 the ESP32 link. Edit CubeMX-generated files only inside 'USER CODE' blocks. The narrative module documents sit in 'doc/' folders next to the code, for example the ESP32 protocol in Protocol.md; the hardware (schematics and PCB) lives in the separate 'WCC-Hardware' repository.
