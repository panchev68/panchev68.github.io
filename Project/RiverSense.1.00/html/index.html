RiverSense firmware

Firmware of an autonomous river-level monitoring node on an STM32U575VGT6 (Cortex-M33, FreeRTOS).

Overview

The node measures the distance to the water surface with an A02YYUW ultrasonic sensor and the water temperature with a DS18B20, and reports to the cloud over HTTPS through an A7670E 4G modem wired directly to the MCU (TLS runs inside the modem). A 6 V GEL accumulator charged from a solar panel powers it; the charger is the MPPT design of the WasteContainerControl project, as on its board hw2.00. Every external device is powered only while it is used, and the processor sleeps in STOP1 between measurements.

APP::Monitor runs the measurement cycle: it measures every 15 minutes and reports every 60 minutes, measures every 2 and reports every 10 minutes for a while after a rapid level change, reports at once on a move of 100 mm or more, and stretches all periods four times when the accumulator is low. The modem is powered off completely after each report. After the modem has registered, APP::Clock sets the RTC from the network time and APP::Site fetches the installation position that APP::PowerSupply uses for its night window. The cloud answers with a JSON command that APP::CommandInterpreter runs. Faults are collected by APP::Diagnostics::Runtime and sent with each report; APP::Diagnostics::Boot checks every device once at start-up and shows the result on the LEDs.

Still pending: the final payload format and the device identity (they wait for the ESP32 client), and the concrete cloud commands. The report body is a provisional JSON.

Layers

APP holds the measurement cycle, the solar charger and low-power control, the diagnostics, the clock, the site position, the cloud link and the command interpreter. Board Supported Peripheral holds the supply switches and the drivers of the external devices (sensors, the two INA219 power monitors, the TMP102 and the modem binding). Hardware Abstraction Layer holds one port singleton per CubeMX peripheral handle. Below them lie the CubeMX-generated code ('Core/', 'Drivers/', 'Middlewares/'), the FreeRTOS support in 'RTOS/FreeRTOS_Support.cpp' and the shared library 'Lib' in 'X:/Lib/IAR/inc/Lib' (ports, chip drivers, 'RTOS' wrappers, the A7670E driver, HTTP and crypto helpers), which is outside this repository and must be present to build.

Build requirements

The project is built with IAR Embedded Workbench for Arm (EWARM) version '10.10.2', installed in 'C:/iar/ewarm-10.10.2'. The language is C++20 with the Libc++ runtime ('–libc++'), no exceptions and no RTTI; the full DLib configuration ('–dlib_config') must not be used together with it. The workspace is 'EWARM/Project.eww', the project 'EWARM/STM32U575VGT6.ewp', the configuration 'STM32U575VGT6' and the linker script 'EWARM/stm32u575xx_flash.icf'. From the command line run 'iarbuild.exe EWARM/STM32U575VGT6.ewp -make STM32U575VGT6' ('-build' for a full rebuild); the build is expected to finish with 0 errors and 0 warnings. In VS Code the IAR extension reads '.vscode/iar-vsc.json'.

The generated layer comes from STM32CubeMX '6.18.1' (database '6.0.181') with the firmware package 'STM32Cube FW_U5 V1.9.0' and the X-CUBE-FREERTOS pack '1.6.0'. That pack carries the FreeRTOS kernel 'V11.2.0' behind the CMSIS-RTOS v2 wrapper, the port 'ARM_CM33_NTZ' and the 'heap_4' allocator. Regenerating from 'STM32U575VGT6.ioc' overwrites everything outside the 'USER CODE' blocks and resets two project settings (the runtime library to the full DLib and the language to C only); the working values are listed in 'CLAUDE.md'. The 'FREERTOS_LOW_POWER_SUPPORT' define in the '.ewp' enables the tickless idle, and the LPTIM1 global interrupt must stay off in CubeMX because 'LowPower.cpp' defines its handler.

The shared library 'Lib' is used at version '3.08' (branch '3.08' of 'X:/Lib/IAR'). The project has no display, so TouchGFX is not needed. This documentation is generated with Doxygen '1.18.0' using '.doxygen/.doxyfile'; its tag files for the library and the standard library are listed in 'TAGFILES' and must exist at the paths given there.

Where to start

Start with APP::Monitor, the measurement cycle, and APP::PowerSupply, the solar charger. The entry point is 'startup()' in 'startup.cpp', run from the default FreeRTOS task after the scheduler starts: it starts APP::LowPower, runs the boot diagnostics before any module owns the hardware, then starts the charger and the measurement cycle.

Every class is a singleton reached through 'instance()'. I2C1 is shared, so only the task of APP::PowerSupply touches the two INA219 monitors; the other tasks read the published accumulator voltage from BSP::Accumulator. The drivers are blocking and meant for task context; the caller powers a rail through BSP::PowerSwitches before 'open()' and calls 'close()' before cutting it. Edit generated code only inside the 'USER CODE' blocks. The board composition and the pin map are in 'doc/Hardware.md', each module has its own Bulgarian description in the 'doc/' folder next to it, and the plan and open questions are in 'Plan.md'.
